    动画层级计算

    biubiubiu 2026/1/22 动画ShellTransitions

    本篇目的：详细介绍动画图层的的计算规则 基于 android-15.0.0_r26

    以在桌面起点电话应用为例

    # 1. Transition::getAnimatableParent 获取可以作为动画的父容器

    # Transition.java
    /** Returns the parent that the remote animator can animate or control. */
    private static WindowContainer<?> getAnimatableParent(WindowContainer<?> wc) {
        // 1. 获取 wc 的直接父容器
        WindowContainer<?> parent = wc.getParent();
        // 2. 如果符合条件就一直向上遍历父容器
        while (parent != null
                && (!parent.canCreateRemoteAnimationTarget() && !parent.isOrganized())) {
            parent = parent.getParent();
        }
        // 3. 返回最终符合要求的容器
        return parent;
    }

    最终能遍历到哪一层父容器，受循环语句里的 2 个方法控制

    # 1.1 WindowContainer::canCreateRemoteAnimationTarget 能否创建远程动画目标

    # WindowContainer.java

    boolean canCreateRemoteAnimationTarget() {
        return false;
    }
    • TaskDisplayArea : 也就是 DefaultTaskDisplayArea ，如果开启了 ShellTransition 就返回 true
    • ActivityRecord : 返回 true
    • TaskFragment : 返回 true

    # 1.2 WindowContainer::isOrganized 容器是否被 WindowOrganizer 管理

    # WindowContainer.java

    /**
     * @return {@code true} if window container is manage by a
     *          {@link android.window.WindowOrganizer}
     */
    boolean isOrganized() {
        return false;
    }

    默认返回 false ， 表示不受管理。 目前只有 3 个类重写了这个方法：

    • TaskDisplayArea : 返回指是 mOrganizer != null
    • Task : 返回指是 mTaskOrganizer != null ,赋值是 ATMS下的 mTaskOrganizerController ，按理说就不会为null
    • TaskFragment : 返回值是 mTaskFragmentOrganizer != null

    # 1.3 小结

    根据上面的代码已经对 2 个方法的解释，可以得出以下结论：

      1. WindowState 返回 ActivityRecord 或者 DisplayContent (Display)
      • 1.1 是应用下 WindowState ,那么它的父容器是 ActivityRecord ，不满足条件，返回值就是 ActivityRecord
      • 1.2 是非应用下 WindowState ，它的父容器不包含上面这些类，所以返回的是 DisplayContent (Display)
      1. ActivityRecord 返回 Task Task::isOrganized 返回true
      1. Task 返回 DefaultTaskDisplayArea 或者 DisplayContent (Display) 取决于有没有开启 ShellTransition
      1. DefaultTaskDisplayArea 返回 DisplayContent (Display) 虽然 TaskDisplayArea 重新了方法， 但是一进来就 getParent 了
      1. 其他上层的，返回 DisplayContent (Display)

    在 Transition::calculateTargets 方法里加上 mChanges 的日志：

    补充

    发现比收集的容器多了很多，仔细对比还是能发现规律：多出来的都是涉及到动画的 2 个应用 ActivityRecord 上面的层级

    # Transition.java
void collect(@NonNull WindowContainer wc) {
        ......
        // 日志
        ProtoLog.v(WmProtoLogGroups.WM_DEBUG_WINDOW_TRANSITIONS, "Collecting in transition %d: %s",
                mSyncId, wc);
        // Snapshot before checking if this is a participant in case it has been re-parented.
        // 收集快照
        snapshotStartState(getAnimatableParent(wc));
        if (mParticipants.contains(wc)) return;
        // Transient-hide may be hidden later, so no need to request redraw.
        if (!isInTransientHide(wc)) {
            // 添加进同步组
            mSyncEngine.addToSyncSet(mSyncId, wc);
        }
        // 一个容器对应一个 ChangeInfo
        ChangeInfo info = mChanges.get(wc);
        if (info == null) {
            info = new ChangeInfo(wc);
            updateTransientFlags(info);
            // 添加
            mChanges.put(wc, info);
        }
        // 添加
        mParticipants.add(wc);
}

    如果这看这里，mChanges 和 mParticipants 应该是一样的，那么 如果这看这里，mChanges 多出来的元素在哪里被添加的呢？ 经过调试发现是在 Transition::snapshotStartState 里

    # 1.2.1 mChanges 其他元素的添加

        /** "snapshot" `wc` and all its parents (as potential promotion targets). */
    // 记录参数 WindowContainer 及其可动画父容器链在转换开始时的状态快照。
    // 这个方法会向上遍历父容器链，直到遇到一个已经记录过状态的容器或者没有更多可动画的父容器为止。
    private void snapshotStartState(@NonNull WindowContainer<?> wc) {

        for (WindowContainer<?> curr = wc;
                curr != null && !mChanges.containsKey(curr);
                curr = getAnimatableParent(curr)) {
            // 为这个容器创建 ChangeInfo
            final ChangeInfo info = new ChangeInfo(curr);
            flag 是否添加 FLAG_TRANSIENT_HIDE
            updateTransientFlags(info);
            mChanges.put(curr, info);
            ......
        }
    }

    可以看到重要的条件还是 Transition::getAnimatableParent 方法。 会不断的遍历父容器，加入 mChanges ，这也就理解了为什么 mChanges 除了收集的容器，还多出来了他们的父容器树（满足条件的父容器）

    框架把这些都记录起来，是因为做动画的时候需要根据它们计算出用哪些容器传递出去做动画
