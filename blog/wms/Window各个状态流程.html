    # 1. 窗口状态的定义

    窗口的状态切换由WindowStateAnimator控制一共有5个状态，定义如下：

    根据代码的注释可知，窗口的状态是根据Surface的状态定义的，所以可以说是窗口状态也可以说是窗口Surface的状态。 代码中的值定义和注释我就不翻译了，笔记最后会对每个状态做总结。

    主要是找到每个状态在代码中哪个流程进行设置的，这样以后遇到问题的时候就可以根据日志或者dump的状态来判断代码的执行流程。至于如何找怎么设置的最简单的方法就是全局搜这几个状态在哪里被赋值使用就好了，还挺简单的。

    搜索到被设置的地方有2处，一个是创建Surface失败的时候，一个是销毁窗口的时候，比较好理解。 先看创建Surface失败的时候：

    为当前创建创建Surface，创建成功就为DRAW_PENDING，失败的话就是NO_SURFACE了，这个没啥问题，然后看看窗口销毁的时候。 窗口销毁有好几个种情况，所以调用链也不一样但是最终设置窗口状态的地方是一样的。

    # WindowStateAnimator

    void destroySurfaceLocked(SurfaceControl.Transaction t) {
        ......
        destroySurface(t);
        ......
        mDrawState = NO_SURFACE;
    }

    void destroySurface(SurfaceControl.Transaction t) {
        // Since the SurfaceControl is getting torn down, it's safe to just clean up any
        // pending transactions that were in mPostDrawTransaction, as well.
        t.merge(mPostDrawTransaction);

        try {
            if (mSurfaceController != null) {
                mSurfaceController.destroy(t);
            }
        } catch (RuntimeException e) {
            Slog.w(TAG, "Exception thrown when destroying surface " + this
                    + " surface " + mSurfaceController + " session " + mSession + ": " + e);
        } finally {
            mWin.setHasSurface(false);
            mSurfaceController = null;
            mDrawState = NO_SURFACE;
        }
    }

    销毁窗口会走到destroySurfaceLocked方法，然后这个方法和气内部执行的destroySurface方法都会将状态设置为NO_SURFACE。 这里整理2个场景的调用链，看看就好。

    # 2.2 DRAW_PENDING

    这个状态应该是窗口正常情况的第一个状态，表示Surface已创建好了，等待进行绘制。这个状态被设置的时候就是在创建Surface的时候。搜索代码的时候发现有2处设置了，但是正常流程应该就是Window创建Surface时候，而Window创建Surface的时机在【Window的大小位置-relayoutWindow-1】提到，是执行relayoutWindow的时候，代码在上面刚好贴了WindowStateAnimator::createSurfaceLocked方法，在执行创建WindowSurfaceController前会执行resetDrawState()方法。

    # WindowStateAnimator

    void resetDrawState() {
        // 设置为DRAW_PENDING
        mDrawState = DRAW_PENDING;

        if (mWin.mActivityRecord == null) {
            return;
        }

        if (!mWin.mActivityRecord.isAnimating(TRANSITION)) {
            mWin.mActivityRecord.clearAllDrawn();
        }
    }

    所以正常情况下执行完relayoutWindow流程后，窗口的状态就为DRAW_PENDING了。

    # 2.3 COMMIT_DRAW_PENDING -- finishDrawing流程

    这个 PENDING 是表示等待的时候，前面2个单词是连起来读的，不要误会了，所以从单词理解就是等待提交绘制的内容。 也就是说应用层已经完成绘制了，等待被提交到surfaceFlinger合成显示。 这个只有 WindowStateAnimator::finishDrawingLocked 一个地方被使用，执行到这个方法的流程也叫finishDrawing流程也是WMS比较重要的一个流程。

# WindowManagerService

    void finishDrawingWindow(Session session, IWindow client,
            @Nullable SurfaceControl.Transaction postDrawTransaction, int seqId) {
        if (postDrawTransaction != null) {
            postDrawTransaction.sanitize();
        }

        final long origId = Binder.clearCallingIdentity();
        try {
            synchronized (mGlobalLock) {
                // 获取到对应的WindowState
                WindowState win = windowForClientLocked(session, client, false);
                // 有log输出
                ProtoLog.d(WM_DEBUG_ADD_REMOVE, "finishDrawingWindow: %s mDrawState=%s",
                        win, (win != null ? win.mWinAnimator.drawStateToString() : "null"));
                // 重点*1. 执行WindowState::finishDrawing
                if (win != null && win.finishDrawing(postDrawTransaction, seqId)) {
                    if (win.hasWallpaper()) {
                        win.getDisplayContent().pendingLayoutChanges |=
                                WindowManagerPolicy.FINISH_LAYOUT_REDO_WALLPAPER;
                    }
                    // 2. 将当前WindowState.mLayoutNeeded置为true
                    win.setDisplayLayoutNeeded();
                    // 3. 请求进行布局刷新
                    mWindowPlacerLocked.requestTraversal();
                }
            }
        } finally {
            Binder.restoreCallingIdentity(origId);
        }
    }

    重点分析：

    1. WindowState::finishDrawing内部会触发窗口状态的刷新，为当前分析路线
    2. setDisplayLayoutNeeded内部将WindowState.mLayoutNeeded置为true，是判断是否进行窗口大小尺寸计算的条件之一
    3. WindowPlacerLocked::requestTraversal也是常见核心函数，触发布局刷新

    这里看到会调用 WindowStateAnimator::finishDrawingLocked 方法，这个方法这小节前面已经看过了。

    # 2.3.2 finishDrawing流程小结

    1. 经过relayoutWindow后应用层就拿到了对应的Surface
    2. 经过View绘制的3个核心步骤后，Surface已经被绘制好了数据
    3. 应用层通过Session::finishDrawing方法通知WMS，已经界面绘制完毕，WMS将窗口状态设置为COMMIT_DRAW_PENDING

    # 2.4 READY_TO_SHOW -- 提交Surface到SurfaceFlinger

    这个步骤是 COMMIT_DRAW_PENDING 的下一步，既然数据已经绘制完毕，那就需要去通知SurfaceFlinger进行处理最终显示到屏幕上了。WMS层向SurfaceFlinger提交后的状态就是READY_TO_SHOW。 READY_TO_SHOW 也只有一个地方被设置 -- WindowStateAnimator::commitFinishDrawingLocked 方法。

    # WindowStateAnimator

    boolean commitFinishDrawingLocked() {
        ......
        // 当前状态的判断，不满足则return
        if (mDrawState != COMMIT_DRAW_PENDING && mDrawState != READY_TO_SHOW) {
            return false;
        }
        // 注意日志
        ProtoLog.i(WM_DEBUG_ANIM, "commitFinishDrawingLocked: mDrawState=READY_TO_SHOW %s",
                mSurfaceController);
        // 设置状态
        mDrawState = READY_TO_SHOW;
        ......
        // 不依赖Activity的Window或者startWindow则会走后续流程设置为 HAS_DRAW
        if (activity == null || activity.canShowWindows()
                || mWin.mAttrs.type == TYPE_APPLICATION_STARTING) {
            result = mWin.performShowLocked();
        }
        return result;
        ......
    }

    不依赖Activity的Window或者startWindow才会继续走 performShowLocked 流程 或者满足第二个条， Activity 也可能在这里走进去的。

    这个调用链是在比较熟悉的WindowPlacerLocked::performSurfacePlacementNoTrace方法，之前在分析relayoutWindow流程说过这个方法之前说过是很复杂的，而且执行多次，不同的场景和条件执行的分支是不一样的，【Window的大小位置-relayoutWindow-2】。

    当执行完finishDrawing流程后，窗口的状态被设置为了COMMIT_DRAW_PENDING，在执行performSurfacePlacementNoTrace方法的时候，就会走到设置为READY_TO_SHOW逻辑了。

    # 2.5 HAS_DRAWN

    上一步先是设置状态为READY_TO_SHOW然后也提交Surface到SufaceFlinger进行合成显示了，那么下一步就是最终的状态，Window处于显示状态--HAS_DRAWN 进入这个设置逻辑也在RootWindowContainer::performSurfacePlacementNoTrace

    # RootWindowContainer
    void performSurfacePlacementNoTrace() {
        ......
        // 开启事务
        mWmService.openSurfaceTransaction();
        try {
            // 处理事务
            applySurfaceChangesTransaction();
        } catch (RuntimeException e) {
            Slog.wtf(TAG, "Unhandled exception in Window Manager", e);
        } finally {
            // 关闭事务。重点* 内部会触发apply， 才是真正将surface提交到SurfaceFlinger
            mWmService.closeSurfaceTransaction("performLayoutAndPlaceSurfaces");
            Trace.traceEnd(TRACE_TAG_WINDOW_MANAGER);
        }
        ......
        // 也可能会 设置为HAS_DRAW 
        // applySurfaceChangesTransaction如果条件满足会触发提交Surface到SrefaceFlinger
        checkAppTransitionReady(surfacePlacer);
        ......
    }

    performSurfacePlacementNoTrace()方法中看到逻辑执行了 applySurfaceChangesTransaction 方法，并且前后各自又打开事务和关闭事务的操作。 applySurfaceChangesTransaction方法处理的事情现在整理出一下3个：

    1. 出触发 relayoutWindow，设置窗口状态为DRAW_PENDING
    2. 执行mApplySurfaceChangesTransaction设置状态为READY_TO_SHOW
    3. 执行prepareSurfaces方法提交Surface到SufaceFlinger

    执行 applySurfaceChangesTransaction 方法前后通过WMS的打开关闭事务方法，内部是有一个sGlobalTransaction事务。 applySurfaceChangesTransaction对surface的处理只是保存在transition中而已，只有执行了closeSurfaceTransaction方法才是真正是将surface提交到了SurfaceFlinger显示。

    然后 applySurfaceChangesTransaction 方法之后执行的 checkAppTransitionReady 方法会触发将窗口状态最终设置为 HAS_DRAWN

    可以看到performSurfacePlacementNoTrace方法触发的 applySurfaceChangesTransaction和checkAppTransitionReady 这两个方法是非常重要的。

        if (mWinAnimator.mDrawState != READY_TO_SHOW || !isReadyForDisplay()) {
            return false;
        }
        ......
        // Force the show in the next prepareSurfaceLocked() call.
        mWinAnimator.mLastAlpha = -1;
        // 打印日志
        ProtoLog.v(WM_DEBUG_ANIM, "performShowLocked: mDrawState=HAS_DRAWN in %s", this);
        // 重点* 设置mDrawState的状态为HAS_DRAWN
        mWinAnimator.mDrawState = HAS_DRAWN;
        mWmService.scheduleAnimationLocked();
        ......
        return true;
    }

    这里会对当前状态做检查，只有满足条件才会将状态设为HAS_DRAWN

    # 2.5.1 解释handleOpeningApps下的需要处理的ActivityRecord是哪来的

    根据上面的代码可以看到处理的是DisplayContent下的mOpeningApps集合

    # DisplayContent
    final ArraySet<ActivityRecord> mOpeningApps = new ArraySet<>();
    final ArraySet<ActivityRecord> mClosingApps = new ArraySet<>();

    这里定义了2个集合，handleOpeningApps处理的是mOpeningApps，handleClosingApps处理的是mClosingApps。前面的逻辑看到是直接通过 mDisplayContent.mOpeningApps的方式调用的，那么这个集合的add操作也是这样的。搜索调用的地方发现除了Test类之外只有在ActivityRecord调用，主要看ActivityRecord::setVisibility方法

    # ActivityRecord
    @VisibleForTesting
    void setVisibility(boolean visible, boolean deferHidingClient) {
        final AppTransition appTransition = getDisplayContent().mAppTransition;
        ......
        if (visible) {
                displayContent.mOpeningApps.add(this);
                mEnteringAnimation = true;
        } else if (mVisible) {
                displayContent.mClosingApps.add(this);
                mEnteringAnimation = false;
        }
        ......
    }

    也就是说参数可见的会被加到mOpeningApps，不可见的会被加到mClosingApps。具体调用ActivityRecord::setVisibility的地方在启动流程中。

    # 3. 整理状态调用链

    设置状态的代码前基本上都有对应的的日志，Proto打开 WM_DEBUG_ANIM 后就搜索 “mDrawState=”

    只有3个状态进行了打印。

    # 3.1 NO_SURFACE

    状态数值:0 状态含义:Surface还没有创建，或者销毁的时候 调用链:

    销毁应用的时候：
    WMS::removeWindow
        WindowState::removeIfPossible
            WindowState::removeImmediately
                WindowStateAnimator::destroySurfaceLocked
                    WindowStateAnimator::destroySurface
起动新Activity,之前Activityfinish的时候：
    ActivityClientController::activityStopped
        ActivityRecord::activityStopped
            ActivityRecord::notifyAppStopped
                ActivityRecord::destroySurfaces
                    ActivityRecord::destroySurfaces
                        WindowState::destroySurface
                            WindowState::destroySurfaceUnchecked
                                WindowStateAnimator::destroySurfaceLocked       -- NO_SURFACE
                                    WindowStateAnimator::destroySurface         -- NO_SURFACE

    创建失败的调用链和下面DRAW_PENDING是一样的

    # 3.2 DRAW_PENDING

    状态数值:1

    状态含义:Surface已创建，但是窗口还没有绘制

    调用链:

    ViewRootImpl::relayoutWindow
    mWindowSession.relayout
        WMS::relayoutWindow
            WMS::createSurfaceControl
                WindowStateAnimator::createSurfaceLocked   
                    WindowStateAnimator::resetDrawState     -- DRAW_PENDING

    # 3.3 COMMIT_DRAW_PENDING

    状态数值:2

    状态含义:应用完成绘制,但是Surface还没有开始显示，将在下一次layout时被显示

    调用链:

    ViewRootImpl::performTraversals
    ViewRootImpl::createSyncIfNeeded   --- 创建绘制完成的回调
    ViewRootImpl::reportDrawFinished   --- 回调的触发，真正执行
        Session::finishDrawing
            WMS::finishDrawingWindow
                WindowState::finishDrawing
                    WindowStateAnimator::finishDrawingLocked  --- COMMIT_DRAW_PENDING

    # 3.4 READY_TO_SHOW

    状态数值:3

    状态含义:绘制请求已提交，正在等待被显示

    调用链:

    RootWindowContainer::performSurfacePlacementNoTrace
    RootWindowContainer::applySurfaceChangesTransaction
        DisplayContent::applySurfaceChangesTransaction
            DisplayContent::mApplySurfaceChangesTransaction  
                WindowStateAnimator::commitFinishDrawingLocked   -- READY_TO_SHOW
                    WindowState::performShowLocked  -- 如果是不依赖Activity的Window或者startWindow则会直接设置为HAS_DRAW

            DisplayContent::prepareSurfaces     -----提交Surface到SufaceFlinger
                WindowContainer::prepareSurfaces
                    WindowState::prepareSurfaces
                         WindowStateAnimator::prepareSurfaceLocked
                            WindowStateAnimator::showSurfaceRobustlyLocked
                                WindowSurfaceController::showRobustly
                                    SurfaceControl.Transaction::show   --- 提交到SufaceFlinger

    # 3.5 HAS_DRAW

    状态数值:4

    状态含义:窗口已经绘制到屏幕上完成，可见了

    调用链:

    RootWindowContainer::performSurfacePlacementNoTrace
    RootWindowContainer::checkAppTransitionReady 
        AppTransitionController::handleAppTransitionReady
            AppTransitionController::handleClosingApps
            AppTransitionController::handleOpeningApps
                ActivityRecord::showAllWindowsLocked
                    WindowState::performShowLocked      --- HAS_DRAWN

    # 4. 整理出performSurfacePlacementNoTrace下各个事情的调用链

    这个方法在很多地方包括屏幕刷新都会掉，所以不管前面的调用链是怎么进来的，从performSurfacePlacementNoTrace开始记录，后面的流程不是说每次执行都会走，只有当满足条件的时候才会执行。 也不记录相关流程具体的调用，只记录会进入什么流程。

    RootWindowContainer::performSurfacePlacementNoTrace
    RootWindowContainer::applySurfaceChangesTransaction
        DisplayContent::applySurfaceChangesTransaction
            DisplayContent::performLayout                          --- relayoutWinodw主要逻辑，触发最终触发computeFrames
            DisplayContent::mApplySurfaceChangesTransaction        --- 触发状态设置为 READY_TO_SHOW （不依赖Activity的Window或者startWindow则会走后续流程设置为HAS_DRAW）
            DisplayContent::prepareSurfaces                        --- 提交Surface到SufaceFlinger
    RootWindowContainer::checkAppTransitionReady                   --- 触发状态设置为 HAS_DRAWN
